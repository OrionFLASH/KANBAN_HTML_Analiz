# Бизнес-требования и системный анализ: KANBAN HTML Analiz

**Версия:** 1.0.5  
**Дата:** 2026-08-31  
**Источник:** `Docs/ToDo KANBAN.txt`

---

## 1. Цель проекта

Разработать сервис на Python для анализа массива данных по **лидам (ПрПр)** и **сделкам** из Excel-отчётов Kanban по 11 территориальным банкам (ТБ). Сервис должен:

- агрегировать данные из 22 файлов (11 «К ПРОДАЖЕ» + 11 «В РАБОТЕ»);
- отслеживать движение каждого лида (`ID ПрПр`) по стадиям с расчётом сроков нахождения;
- формировать сводную статистику (min, max, перцентили) в разрезе **продукт / группа продуктов / ТБ**;
- экспортировать результаты в **Excel** (с форматированием) и **JSON** (для будущих HTML-графиков с фильтрацией).

## 2. Заинтересованные стороны и пользователи

| Роль | Потребность |
|------|-------------|
| Аналитик продаж | Понимать типичные и экстремальные сроки прохождения лидов по стадиям для каждого продукта |
| Руководитель ТБ | Сравнивать сроки в разрезе своего ТБ |
| Разработчик HTML-дашборда | Получать структурированный JSON для построения интерактивных графиков |

## 3. Входные данные

### 3.1. Источники

| Режим | Каталог | Файлы |
|-------|---------|-------|
| **test** | `Docs/FileIN/` | `2ГОСБ1ТБ.xlsx` (и опционально другие) |
| **prod** | `IN/` (корень проекта) | 22 файла Kanban от 27-08-2026 (см. §3.2) |

Режим и пути задаются в `config.json`.

### 3.2. Имена prod-файлов (11 ТБ × 2 категории)

**В РАБОТЕ:** ЮЗБ, ЦЧБ, УБ, СРБ, СибБ, СЗБ, ПБ, МБ, ВВБ, ДВБ, ББ  
**К ПРОДАЖЕ:** те же 11 ТБ

Шаблон имени: `Канбан {ТБ} ({КАТЕГОРИЯ}) все на 27-08-2026.xlsx`

### 3.3. Структура Excel

- Лист: `Sheet1`
- Таблица: без имени (опционально может быть названа `СпартТбалица`)
- Объём: **> 1 млн строк** суммарно → требуется параллельная загрузка и обработка

### 3.4. Ключевые колонки

| Колонка | Назначение |
|---------|------------|
| `Дата отчета` | Снимок данных; один лид может встречаться на нескольких датах |
| `ID ПрПр` | Уникальный идентификатор лида |
| `Дата начала работы` | Дата создания лида |
| `Текущий статус` | Основная стадия Kanban |
| `Стадия сделки` | Подстадия (опциональна, может повторяться в разных «Текущий статус») |
| `Количество дней на текущей стадии` | Срок на текущей стадии (из отчёта) |
| `Количество дней с создания сделки` | Срок с момента создания сделки |
| `Дата создания сделки` | Начало работы со сделкой |
| `Группа продукта`, `Продукт` | Классификация продукта |
| `ТБ` | Территориальный банк |
| `_Изменение условий`, `_Ввод данных`, `ЕФС флаг` | Бинарные фильтры (0/1) |
| `Метка` | Текстовый фильтр: «Стратегия» и/или «Стратегия + 2026» (взаимоисключающие в HTML) |
| `КМ` | ФИО менеджера — аналитика превышений P80 |

### 3.5. Справочник стадий «Текущий статус»

1. К ПРОДАЖЕ  
2. АКТИВАЦИЯ ПРОДУКТА  
3. ВЫЯВЛЕНИЕ ПОТРЕБНОСТИ  
4. ОБСУЖДЕНИЕ УСЛОВИЙ  
5. РЕАЛИЗАЦИЯ СДЕЛКИ  

Подстадии «Стадия сделки» — обширный перечень (см. исходное ТЗ), привязаны к родительской стадии.

## 4. Бизнес-логика обработки

### 4.1. Этап 1 — Загрузка и объединение

```
[Excel₁..Excel₂₂] → параллельное чтение → единый DataFrame
```

- Чтение только нужных колонок (экономия памяти).
- Добавление служебных полей: `source_file`, `source_category` (К ПРОДАЖЕ / В РАБОТЕ).

### 4.2. Этап 2 — Справочники (дедупликация)

Из объединённого DataFrame извлечь уникальные:

1. **ТБ**
2. **Текущий статус** → вложенные **Стадии сделки** (many-to-many: одна подстадия может быть в нескольких родительских стадиях)
3. **Группа продукта + Продукт**

### 4.3. Этап 3 — Трекинг лида по стадиям

Для каждого `ID ПрПр`:

1. Найти все комбинации `(Текущий статус [, Стадия сделки])`, в которых лид встречался.
2. При нескольких строках на одну стадию (разные `Дата отчета`):
   - **Правило (из ТЗ):** брать значение дней из **более поздней** `Дата отчета`, содержащей эту стадию.
   - Альтернатива (требует уточнения): max(`Количество дней на текущей стадии`).
3. Сохранить для каждой стадии лида:
   - `days_on_stage` — дни на стадии;
   - `days_since_deal` — дни с создания сделки (если применимо);
   - контекст: `Группа продукта`, `Продукт`, `ТБ`.

### 4.4. Этап 4 — Агрегация статистики

Группировки:

| Уровень | Ключ группировки |
|---------|------------------|
| Общий | `(Группа продукта, Продукт, Текущий статус [, Стадия сделки])` |
| По ТБ | `(ТБ, Группа продукта, Продукт, Текущий статус [, Стадия сделки])` |

Метрики на каждую группу:

- `min`, `max`
- Перцентили (по умолчанию 20, 50, 80 — настраиваются в `config.json`)
- `count` — число лидов с данной стадией
- **P80 КМ ≥** (Excel): для P80 — число **уникальных КМ** с сроком **≥** значения P80 в группе (группа × стадия × ТБ)

### 4.5. Этап 5 — Фильтрация

| Контекст | Поведение |
|----------|-----------|
| **Excel** | Фильтры с `enabled: true` в config; объединение **AND** |
| **JSON** | Комбинации фильтров с `html_slice: true` в `visualizations.filter_slices`; config-only (`efs_flag`) применяется к базе до комбинаций |
| **HTML** | Переключатели ВКЛ/ВЫКЛ по `filter_catalog`; ЕФС **не** в UI — только через config |

| Фильтр | Колонка | Логика |
|--------|---------|--------|
| Изменение условий | `_Изменение условий` | = 1; HTML + JSON комбинации |
| Ввод данных | `_Ввод данных` | = 1; HTML + JSON комбинации |
| ЕФС | `ЕФС флаг` | = 1; **только config** (`html_slice: false`), без UI и без срезов в JSON |
| Стратегия | `Метка` | содержит «Стратегия» |
| Стратегия · 2026 | `Метка` | содержит «Стратегия» **и** «2026» |
| Отказ (стадия / статус) | `Стадия сделки` **или** `Текущий статус` | исключить строки с «отказ» (`exclude_deal_otkaz`, `also_column_keys`) |
| Закрыта (стадия сделки) | `Стадия сделки` | исключить строки с «закрыта» (`exclude_deal_zakryta`) |
| Заключен (стадия сделки) | `Стадия сделки` | исключить строки с «заключен» (`exclude_deal_zaklyuchen`) |

> **Решение (v1.0.2):** `enabled` — AND для Excel и config-only фильтров. HTML-фильтры (`html_slice: true`) — все комбинации 2^N в JSON; `enabled` на них **не** влияет.

> **Решение (v1.0.6):** терминальные стадии — **построчное** исключение на этапе трекинга (лид × дата отчёта), не отсекают весь `ID ПрПр`. Пустая стадия не фильтруется. «Отказ» проверяется в «Стадии сделки» **и** в «Текущем статусе». По умолчанию все три исключения **ВКЛ** в UI и Excel.

### 4.6. Этап 6 — Аналитика менеджеров (КМ)

- Порог P80 по группе × продукт × стадия из общей сводки (без ТБ)
- Превышение: срок лида **строго больше** P80
- Топ-N менеджеров на каждый ТБ по числу превышений (только КМ с нарушениями)
- **Актуальная выгрузка:** при нескольких «Дата отчета» в исходнике — для КМ берётся только `max(Дата отчета)` (`use_latest_report_date`)
- Bar-графики в HTML: число КМ с нарушениями по ТБ и по группам/продуктам
- **Hotspots** — топ зон превышения на каждого КМ (продукт×стадия, +N дн. к P80)
- **`stuck_items`** в hotspot — зависшие лиды/сделки: Клиент, ИНН, ID ПрПр, ID сделки, дней, +P80
- **`rank_selection`** — пул групп/продуктов, метка, ЕФС, изменение условий для TOP-N; полные `records` в JSON
- Выход: лист Excel «Менеджеры», JSON с `records` + `exceedances` + `top_by_tb` / `top_by_tb_grouped`, UI — секции по ТБ и детальная карточка
- Колонки `КМ`, `Метка`, `ID сделки`, `ИНН`, `Клиент` — в `required_column_keys` для загрузки из Excel

## 5. Выходные данные

### 5.1. Каталог

`OUT/` — все файлы с **timestamp** в имени: `YYYYMMDD_HHMMSS`

### 5.2. Excel

| Лист | Содержание |
|------|------------|
| `Сводная` | ТБ × Группа × Продукт × Стадия × min/max/перцентили |
| `Общий` | Без разреза ТБ |
| `{ТБ}` | Отдельный лист на каждый ТБ |
| `Менеджеры` | Топ-N КМ по ТБ + «Топ зон» (каждое отклонение с новой строки, перенос текста) |

> Листы **«Матрица»** и **«Графики»** в Excel не формируются. Интерактивные графики и матрица — в HTML.

Форматирование: условная раскраска (min — зелёный градиент, max — красный, перцентили — нейтральные оттенки).

### 5.3. JSON

**Основной** (`kanban_report_{timestamp}.json` + split-bundle `_html/`):

- `meta` — режим, filters_applied, aggregation modes, bundle_version
- `dimensions` — ТБ, стадии, продукты
- `visualizations.filter_slices` — срезы pipeline-фильтров (`html_slice: true`)
- `visualizations.filter_catalog` — описание фильтров для HTML
- Slim-архив `.json` — указатель на manifest (при `write_monolith_archive: true`)

**Менеджеры** (`kanban_report_managers_{timestamp}.json`):

- `meta.report_date_snapshot` — дата актуального среза (max «Дата отчета»)
- `records[]` — лиды×стадии **только актуальной выгрузки**
- `exceedances[]` — только отклонения P80 (lead_id, deal_id, inn, client, overshoot)
- `top_by_tb[]` / `top_by_tb_grouped[]` с **`hotspots`** и **`stuck_items`** — предрасчёт по `rank_selection`
- `meta.rank_selection`, `dimensions`, `charts` (`by_tb`, `facts`)
- `detail_by_product`, `manager_totals` — всегда в файле

> Копии `*_latest*` и запись в `HTML/data/` **не создаются**. JSON загружается в дашборд вручную.

### 5.4. HTML-дашборд

Каталог `HTML/` — локальная страница; JSON загружается вручную из `OUT/`.

| Раздел | Поведение |
|--------|-----------|
| Графики линий | Кривые «лиды × дни» по срезам `filter_slices` |
| Графики КМ | Bar-chart по блоку `managers.charts` в основном JSON |
| Матрица | `pivot_flat` из активного среза; ячейка: дни + ↑/↓ порога P80 |
| Менеджеры (вкладка) | Опционально (`show_managers_tab`); секции по ТБ, топ-3 нарушителя P80; hotspots + ИНН / ID ПрПр / ID сделки |
| Отбор TOP КМ | Config: `rank_selection`; UI: мультивыбор + «Метка (отбор TOP)» на вкладке менеджеров |

> В UI загружается **один** monolith JSON. Блок `managers` встраивается при `html_json.embed_managers: true`. Отдельная загрузка файла менеджеров **не поддерживается**.

### 6.2. Технологический стек

| Компонент | Выбор | Ограничение |
|-----------|-------|-------------|
| Python | 3.12 | — |
| pandas | чтение/агрегация | Anaconda ✓ |
| openpyxl | запись Excel | Anaconda ✓ |
| concurrent.futures | параллелизм | stdlib ✓ |
| **pip install** | **запрещён** | — |

### 6.3. Производительность

- `ProcessPoolExecutor` для чтения файлов (I/O-bound + GIL).
- Чтение только нужных колонок + `dtype` оптимизация.
- Промежуточные parquet/csv — **не планируется** (stdlib constraint, unless pyarrow in conda — уточнить).
- Chunked aggregation при нехватке RAM — заложить в ROADMAP как fallback.

## 9. Согласованные решения (v1.0.7, 2026-08-31)

| Тема | Решение |
|------|---------|
| Расчёт сроков | Оба метода в коде; переключатель `duration_source`: `columns` / `dates` |
| Подстадии | `stage_analysis_mode: status` (зафиксирован); фильтр уровня в HTML скрыт |
| Фильтры HTML | `html_slice: true` — комбинации в JSON + UI; `enabled` только для Excel |
| Config-only | ЕФС, терминальные `exclude_deal_*`, опционально `exclude_current_for_sale` («К ПРОДАЖЕ») |
| JSON export | Monolith по умолчанию (file://); split — опционально |
| Менеджеры | P80 overall; TOP-3 по ТБ; при `rank_by_team` — участники команды; вкладка HTML опциональна (`show_managers_tab`, по умолчанию `false`) |
| Матрица HTML | Ячейка: ⅔ дни, ⅓ ↑ выше / ↓ ≤ порога |
| Excel визуализация | Листы «Графики» и «Матрица» не создаются; интерактив — только HTML |
| Перцентили | Список `[20, 50, 80]`; Excel: `le_count` / `gt_count` / `km_count` для P80 |
| Workers | `os.cpu_count()` при `parallel_workers=0` |

## 10. Критерии приёмки

- [v] Загрузка test-файла `2ГОСБ1ТБ.xlsx` без ошибок
- [v] Корректные справочники ТБ / стадий / продуктов
- [v] Для каждого продукта — min/max/перцентили по каждой стадии
- [v] Отдельные листы Excel по ТБ + сводная
- [v] JSON пригоден для фильтрации по ТБ/продукту/стадии и pipeline-фильтрам (filter_slices)
- [v] HTML-дашборд: графики, матрица ↑/↓, pipeline + locked-фильтры, менеджеры с командой
- [v] Фильтры: config-only ЕФС / терминальные / «К ПРОДАЖЕ»; HTML — стратегия
- [v] Excel: колонки «П80 КМ ≥», «П80 лидов ≤ / >»
- [ ] Prod-режим читает все 22 файла параллельно
- [v] Выходные файлы в `OUT/` с timestamp
- [v] `team_files` + TOP по участникам команды (лидер лида/сделки, КМ, ВКС)

## 11. Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| OOM на 1M+ строк | Высокая | chunked read, only needed columns, workers limit |
| Несогласованность имён колонок между файлами | Средняя | валидация schema при загрузке |
| Дубли ID ПрПр на одну дату | Средняя | dedup rule + log warning |
| Различие «дни из колонки» vs «дни из дат» | Высокая | configurable `duration_source` |
| openpyxl медленная запись больших листов | Средняя | агрегировать до записи, не сырые данные |
