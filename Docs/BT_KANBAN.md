# Бизнес-требования и системный анализ: KANBAN HTML Analiz

**Версия:** 1.0.1  
**Дата:** 2026-08-31  
**Источник:** `Docs/ToDo KANBAN.txt`

---

## 1. Цель проекта

Разработать сервис на Python для анализа массива данных по **лидам (ПрПр)** и **сделкам** из Excel-отчётов Kanban по 11 территориальным банкам (ТБ). Сервис должен:

- агрегировать данные из 22 файлов (11 «К ПРОДАЖЕ» + 11 «В РАБОТЕ»);
- отслеживать движение каждого лида (`ID ПрПр`) по стадиям с расчётом сроков нахождения;
- формировать сводную статистику (min, max, перцентили) в разрезе **продукт / группа продуктов / ТБ**;
- экспортировать результаты в **Excel** (с форматированием) и **JSON** (для будущих HTML-графиков с фильтрацией).

## 2. Заинтересованные стороны и пользователи

| Роль | Потребность |
|------|-------------|

| Руководитель ТБ | Сравнивать сроки в разрезе своего ТБ |
| Разработчик HTML-дашборда | Получать структурированный JSON для построения интерактивных графиков |

## 3. Входные данные

### 3.1. Источники

| Режим | Каталог | Файлы |
|-------|---------|-------|
| **test** | `Docs/FileIN/` | `2ГОСБ1ТБ.xlsx` (и опционально другие) |
| **prod** | `IN/` (корень проекта) | 22 файла Kanban от 27-08-2026 (см. §3.2) |

Режим и пути задаются в `config.json`.

### 3.2. Имена prod-файлов (11 ТБ × 2 категории)

**В РАБОТЕ:** ЮЗБ, ЦЧБ, УБ, СРБ, СибБ, СЗБ, ПБ, МБ, ВВБ, ДВБ, ББ  
**К ПРОДАЖЕ:** те же 11 ТБ

Шаблон имени: `Канбан {ТБ} ({КАТЕГОРИЯ}) все на 27-08-2026.xlsx`

### 3.3. Структура Excel

- Лист: `Sheet1`
- Таблица: без имени (опционально может быть названа `СпартТбалица`)
- Объём: **> 1 млн строк** суммарно → требуется параллельная загрузка и обработка

### 3.4. Ключевые колонки

| Колонка | Назначение |
|---------|------------|
| `Дата отчета` | Снимок данных; один лид может встречаться на нескольких датах |
| `ID ПрПр` | Уникальный идентификатор лида |
| `Дата начала работы` | Дата создания лида |
| `Текущий статус` | Основная стадия Kanban |
| `Стадия сделки` | Подстадия (опциональна, может повторяться в разных «Текущий статус») |
| `Количество дней на текущей стадии` | Срок на текущей стадии (из отчёта) |
| `Количество дней с создания сделки` | Срок с момента создания сделки |
| `Дата создания сделки` | Начало работы со сделкой |
| `Группа продукта`, `Продукт` | Классификация продукта |
| `ТБ` | Территориальный банк |
| `_Изменение условий`, `_Ввод данных`, `ЕФС флаг` | Бинарные фильтры (0/1) |
| `Метка` | Текстовый фильтр: «Стратегия» и/или «Стратегия + 2026» (взаимоисключающие в HTML) |
| `КМ` | ФИО менеджера — аналитика превышений P80 |

### 3.5. Справочник стадий «Текущий статус»

1. К ПРОДАЖЕ  
2. АКТИВАЦИЯ ПРОДУКТА  
3. ВЫЯВЛЕНИЕ ПОТРЕБНОСТИ  
4. ОБСУЖДЕНИЕ УСЛОВИЙ  
5. РЕАЛИЗАЦИЯ СДЕЛКИ  

Подстадии «Стадия сделки» — обширный перечень (см. исходное ТЗ), привязаны к родительской стадии.

## 4. Бизнес-логика обработки

### 4.1. Этап 1 — Загрузка и объединение

```
[Excel₁..Excel₂₂] → параллельное чтение → единый DataFrame
```

- Чтение только нужных колонок (экономия памяти).
- Добавление служебных полей: `source_file`, `source_category` (К ПРОДАЖЕ / В РАБОТЕ).

### 4.2. Этап 2 — Справочники (дедупликация)

Из объединённого DataFrame извлечь уникальные:

1. **ТБ**
2. **Текущий статус** → вложенные **Стадии сделки** (many-to-many: одна подстадия может быть в нескольких родительских стадиях)
3. **Группа продукта + Продукт**

### 4.3. Этап 3 — Трекинг лида по стадиям

Для каждого `ID ПрПр`:

1. Найти все комбинации `(Текущий статус [, Стадия сделки])`, в которых лид встречался.
2. При нескольких строках на одну стадию (разные `Дата отчета`):
   - **Правило (из ТЗ):** брать значение дней из **более поздней** `Дата отчета`, содержащей эту стадию.
   - Альтернатива (требует уточнения): max(`Количество дней на текущей стадии`).
3. Сохранить для каждой стадии лида:
   - `days_on_stage` — дни на стадии;
   - `days_since_deal` — дни с создания сделки (если применимо);
   - контекст: `Группа продукта`, `Продукт`, `ТБ`.

### 4.4. Этап 4 — Агрегация статистики

Группировки:

| Уровень | Ключ группировки |
|---------|------------------|
| Общий | `(Группа продукта, Продукт, Текущий статус [, Стадия сделки])` |
| По ТБ | `(ТБ, Группа продукта, Продукт, Текущий статус [, Стадия сделки])` |

Метрики на каждую группу:

- `min`, `max`
- Перцентили (по умолчанию 20, 50, 80 — настраиваются в `config.json`)
- `count` — число лидов с данной стадией

### 4.5. Этап 5 — Фильтрация

| Контекст | Поведение |
|----------|-----------|
| **Excel** | Фильтры с `enabled: true` в config; объединение **AND** |
| **JSON** | Предрасчёт всех комбинаций ключей `config.filters` в `visualizations.filter_slices` (пустые пропускаются) |
| **HTML** | Переключатели ВКЛ/ВЫКЛ по `filter_catalog`; варианты метки в одной `exclusive_group` — не более одного активного |

| Фильтр | Колонка | Логика |
|--------|---------|--------|
| Изменение условий | `_Изменение условий` | = 1 |
| Ввод данных | `_Ввод данных` | = 1 |
| ЕФС | `ЕФС флаг` | = 1 |
| Стратегия | `Метка` | содержит «Стратегия» |
| Стратегия · 2026 | `Метка` | содержит «Стратегия» **и** «2026» |

> **Решение (v1.0):** фильтры комбинируются через **AND**. Для HTML все комбинации предрасчитываются в JSON; `enabled` влияет только на Excel.

### 4.6. Этап 6 — Аналитика менеджеров (КМ)

- Порог P80 по группе × продукт × стадия из общей сводки (без ТБ)
- Превышение: срок лида **строго больше** P80
- Топ-3 менеджера на каждый ТБ по числу превышений
- Выход: лист Excel «Менеджеры», отдельный JSON, блок BOTTOM в HTML-дашборде
- Колонка `КМ` должна быть в `required_column_keys` для загрузки из Excel

## 5. Выходные данные

### 5.1. Каталог

`OUT/` — все файлы с **timestamp** в имени: `YYYYMMDD_HHMMSS`

### 5.2. Excel

| Лист | Содержание |
|------|------------|
| `Сводная` | ТБ × Группа × Продукт × Стадия × min/max/перцентили |
| `Общий` | Без разреза ТБ |
| `{ТБ}` | Отдельный лист на каждый ТБ |
| `Матрица` | Продукт/группа × стадия, фильтры |
| `Графики` | Кривые «лиды × дни» |
| `Менеджеры` | Топ-3 КМ по ТБ (превышения P80), если есть колонка КМ |

Форматирование: условная раскраска (min — зелёный градиент, max — красный, перцентили — нейтральные оттенки).

### 5.3. JSON

**Основной** (`kanban_report_*.json`):

- `meta` — режим, filters_applied (Excel), aggregation modes
- `dimensions` — ТБ, стадии, продукты, filter_dimensions
- `statistics` — агрегаты overall / by_tb (обе агрегации: group_product, group_only)
- `visualizations.filter_slices` — предрасчитанные срезы pipeline-фильтров
- `visualizations.filter_catalog` — описание фильтров для HTML

**Менеджеры** (`kanban_report_managers_*.json`):

- `top_by_tb`, `detail_by_product`, `manager_totals`, `meta`

> **Решение (v1.0):** только агрегаты (без lead_tracks). HTML строит матрицу из `pivot_flat`.

### 5.4. HTML-дашборд

Каталог `HTML/` — локальная страница: графики, матрица, pipeline-фильтры, блок менеджеров. Автозагрузка JSON из `HTML/data/` после `run.py`.

### 6.2. Технологический стек

| Компонент | Выбор | Ограничение |
|-----------|-------|-------------|
| Python | 3.12 | — |
| pandas | чтение/агрегация | Anaconda ✓ |
| openpyxl | запись Excel | Anaconda ✓ |
| concurrent.futures | параллелизм | stdlib ✓ |
| **pip install** | **запрещён** | — |

### 6.3. Производительность

- `ProcessPoolExecutor` для чтения файлов (I/O-bound + GIL).
- Чтение только нужных колонок + `dtype` оптимизация.
- Промежуточные parquet/csv — **не планируется** (stdlib constraint, unless pyarrow in conda — уточнить).
- Chunked aggregation при нехватке RAM — заложить в ROADMAP как fallback.

## 8. Нефункциональные требования

| ID | Требование |
|----|------------|
| NFR-01 | Обработка 1M+ строк без падения (≤ 16 GB RAM — целевое) |
| NFR-02 | Повторяемость: одинаковый вход → одинаковый выход |
| NFR-03 | Все параметры в config, без хардкода |
| NFR-04 | Timestamp в именах выходных файлов |
| NFR-05 | Логирование INFO + DEBUG |
| NFR-06 | Без установки pip-пакетов |

## 9. Согласованные решения (v1.1, 2026-08-31)

| Тема | Решение |
|------|---------|
| Расчёт сроков | Оба метода в коде; переключатель `duration_source`: `columns` / `dates` |
| Подстадии | `stage_analysis_mode`: `status` / `substages` / `both` |
| Фильтры | Каждый вкл/выкл в config (`enabled`); AND для Excel; все комбинации в JSON для HTML |
| JSON filter_slices | `dashboard.precompute_html_filter_slices`; обе агрегации group_product / group_only |
| Менеджеры (КМ) | P80 overall; топ-3 на ТБ; `km` в required_column_keys |
| Excel-таблица | Имя в config (`excel_table_name`: `Base`); авто fallback на Sheet1 |
| JSON | Только агрегаты (без lead_tracks) |
| Категория файла | Объединять (не влияет на аналитику) |
| Дубли / срок лида | Max дней на стадии; при равенстве — max `Дата отчета` |
| Перцентили | Настраиваемый список, default `[20, 50, 80]` |
| Workers | `os.cpu_count()` при `parallel_workers=0` |
| Excel | green_red + autofilter + freeze + ширина + формат чисел |

## 11. Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| OOM на 1M+ строк | Высокая | chunked read, only needed columns, workers limit |
| Несогласованность имён колонок между файлами | Средняя | валидация schema при загрузке |
| Дубли ID ПрПр на одну дату | Средняя | dedup rule + log warning |
| Различие «дни из колонки» vs «дни из дат» | Высокая | configurable `duration_source` |
| openpyxl медленная запись больших листов | Средняя | агрегировать до записи, не сырые данные |
